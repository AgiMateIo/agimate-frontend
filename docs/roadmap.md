# Roadmap — админ-управление платформенными записями

Сделанное отсюда вычищено: платформенный LLM-провайдер с квотами, справочник
пользователей со сменой роли и раздел админки в навигации уже в `main`.

Роль ADMIN определяется по `user.role === 'ADMIN'` из `GET /user/me` (`src/hooks/useIsAdmin.ts`).
Гейтинг — только для UX; бэк всё равно проверяет права и возвращает `403`.

Осталось две идеи. Обе описаны коротко намеренно: контракт бэкенда под ними не сверялся
и под пресетами точно уехал, так что подробный план полей и эндпоинтов был бы выдумкой.
Начинать — со сверки с бэкендом.

## 1. Системные скилы

Дать админу создавать и править платформенные скилы прямо в дашборде: бейдж «Системный»
в списке, кнопка создания, снятие с публикации. Из этого есть только `system?: boolean`
в `SkillResponse` — причём гейт правки сейчас сделан **наоборот** от нужного
(`isEditable = user.id === skill.userId && !skill.system` в
`src/app/[locale]/dashboard/skills/[id]/page.tsx`), то есть админ системный скилл
редактировать не может.

Открытый вопрос: `SkillForm` редактирует сырой `skillMd` одной textarea, а name живёт
во frontmatter внутри неё — как сделать name read-only, если бэкенд запрещает
переименование системного скилла.

## 2. Пресеты ролей агента

Админский CRUD пресетов (`/dashboard/admin/presets`) вместо правки в БД: список, включая
выключенные, создание и редактирование, retire вместо удаления. Сейчас на фронте только
чтение галереи для мастера создания агента.

Учесть при сверке: тип `AgentPresetResponse` описывает пресет как чистый prefill мастера —
бэкенд не знает ни про какое «применение», и админские поля (порядок, включённость)
в нём отсутствуют. Секция добавляется в `SECTIONS` в
`src/components/layout/AdminContextNav.tsx` — отдельного пункта сайдбара у админки нет.

## Вне области

- Версионирование пресетов / draft-publish скилов — нет.
- Несколько платформенных LLM-провайдеров — только один (синглтон `name: "platform"`).
